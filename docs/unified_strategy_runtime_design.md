# Unified Strategy Runtime Design

## Goal

Make strategy code identical in backtest and live mode.

The switching rule should be:

- same strategy DLL
- same strategy parameters
- same event model
- same order lifecycle
- only the runtime adapter changes

In practice, a strategy should not contain:

- `if (context.mode() == Backtest) ... else ...`
- backtest-only local fill simulation
- file-boundary-only logic
- synthetic account bookkeeping

Those behaviors belong to the runtime, not the strategy.

## Core Principle

The strategy layer must be a deterministic state machine over a unified event stream.

That means:

- the strategy reads market/account/order events
- the strategy updates its own internal state
- the strategy emits trading intents
- the runtime executes those intents in either backtest or live mode

If the same event sequence is replayed, the same strategy code must make the same decisions.

## Layer Split

### 1. Strategy Layer

Responsibilities:

- alpha / signal logic
- position management rules
- order intent generation
- strategy-local state

Must not do:

- local matching engine
- local pnl accounting
- live-only order handling
- backtest-only synthetic fill shortcuts

### 2. Runtime Engine Layer

Responsibilities:

- drive the event loop
- feed ticks / bars / session events
- manage order state machine
- maintain account / position snapshots
- route intents to execution adapter
- persist and restore runtime state

This layer must be shared by both backtest and live mode.

### 3. Adapter Layer

Two interchangeable adapters:

- `BacktestAdapter`
- `LiveAdapter`

Backtest adapter:

- replays AGTICK data
- simulates broker acknowledgements and fills
- exposes the same order lifecycle events as live

Live adapter:

- subscribes to CTP market data
- submits real broker orders
- converts broker callbacks into the same order lifecycle events

The strategy should not know which adapter is underneath.

## Unified Event Model

Backtest and live must both feed the strategy through the same event types.

Recommended event set:

- `TickEvent`
- `BarClosedEvent`
- `TradingDayStartEvent`
- `TradingDayEndEvent`
- `SessionOpenEvent`
- `SessionCloseEvent`
- `OrderAcceptedEvent`
- `OrderRejectedEvent`
- `OrderPartiallyFilledEvent`
- `OrderFilledEvent`
- `OrderCancelledEvent`
- `PositionSyncEvent`
- `TimerEvent`

Current project already has tick and order events, but bars, session boundaries, and recovery/sync events should be promoted to first-class runtime events.

## Unified Order Model

Strategies should submit `OrderIntent`, not backtest-special requests.

Recommended structure:

- `client_order_id`
- `instrument`
- `exchange`
- `side`
- `offset_policy`
- `price_policy`
- `quantity`
- `time_in_force`
- `tag`

Key point:

- the strategy says what it wants
- the runtime decides how to realize it in the current mode

Examples:

- `price_policy = JoinBestBid`
- `price_policy = JoinBestAsk`
- `price_policy = CrossWithOffset(+10 ticks)`
- `time_in_force = IOC`
- `offset_policy = Auto`

Then:

- backtest adapter simulates the order with the same lifecycle
- live adapter turns it into the appropriate CTP order

## Offset Handling

Strategies should not manually decide `CloseToday` vs `CloseYesterday` in most cases.

Instead use:

- `OffsetPolicy::Auto`
- `OffsetPolicy::OpenOnly`
- `OffsetPolicy::CloseOnly`

Runtime resolves:

- SHFE/INE close-today / close-yesterday rules
- current available today/yesterday positions
- partial close sequencing

This keeps strategy code identical across modes.

## Market Data Contract

Every market event should carry a normalized numeric payload.

Recommended hot-path fields:

- `timestamp_ms`
- `trading_day`
- `instrument_id`
- `exchange_id`
- `last`
- `bid1`
- `ask1`
- `bid1_size`
- `ask1_size`
- `cum_volume`
- `cum_turnover`

String fields may still exist for UI/debug, but strategy/runtime hot path should primarily use numeric fields.

## Bar Generation

Bars should be generated by the runtime, not by each strategy independently.

Reason:

- guarantees identical bar-close timing in backtest and live
- avoids strategy-specific bar edge bugs
- lets multiple strategies share the same bar feed

Recommended:

- runtime bar aggregator keyed by instrument + timeframe
- strategy subscribes to required timeframes
- runtime emits `BarClosedEvent`

This is especially important for current `mode16`, because the strategy now embeds minute-bar construction and session-boundary logic locally.

## Position and Account Views

Strategies should consume read-only runtime views:

- `PositionView`
- `AccountView`
- `OpenOrdersView`

These views should come from the runtime, not from strategy-local bookkeeping.

The strategy may keep derived local state, but broker/runtime state remains the source of truth.

## Recovery and Restart

For live mode, restart safety must be built into the runtime.

Recommended options:

- persist strategy state snapshots
- persist order mapping `client_order_id -> broker_order_id`
- restore broker positions and open orders on startup
- emit `PositionSyncEvent` and `OpenOrdersSyncEvent` before regular ticks begin

Without this, identical strategy code is not enough for safe live operation.

## Rules for New Strategies

All future strategies should follow these rules:

- no `context.mode()` branching in strategy logic
- no backtest-only fill hacks
- no local pnl bookkeeping as execution truth
- no file-boundary-only logic
- no strategy-owned matching engine
- all orders go through runtime order intent API
- all bars come from runtime bar events
- all state transitions react to runtime events

## Migration Plan for Current Project

### Phase 1. Runtime API upgrade

Add these runtime capabilities:

- `submit_intent(OrderIntent)`
- `cancel_order(client_order_id)`
- `replace_order(client_order_id, OrderIntent)`
- `account_view()`
- `position_view(instrument)`
- `open_orders_view(instrument)`
- `now_ms()`
- `trading_day()`

### Phase 2. Shared execution state machine

Move order lifecycle logic from strategy into runtime:

- pending order tracking
- queue / fill state
- cancel / replace transitions
- final order events

Backtest and live both use this same state machine.

### Phase 3. Shared bar/session engine

Move these concerns from strategy into runtime:

- bar aggregation
- session open/close detection
- trading-day boundaries

### Phase 4. Refactor current `ag_breakout_strict_strategy`

Current strategy should be split into:

- pure decision logic
- runtime-driven order handling

Specifically remove from strategy:

- local queue matcher
- `backtest_force_fill`
- file-boundary forced close
- backtest-only early return in live mode

### Phase 5. Live-ready mode16

After the above:

- same DLL runs in backtest and live
- only configuration changes
- runtime adapter decides simulated or real execution

## What Must Change in This Repo

To fully reach the goal, these current project mechanisms should be retired or isolated:

- `OrderRequest.backtest_force_fill`
- strategy-local fill simulation in `ag_breakout_strict_strategy`
- strategy-local bar engine for mode16
- direct dependence on file boundaries inside strategy code

Those were useful to port the source backtest accurately, but they are not the correct foundation for a unified live/backtest strategy architecture.

## Definition of Done

The architecture is complete when:

- one strategy DLL runs unchanged in both backtest and live
- the strategy contains no mode-specific code path
- runtime emits the same event contract in both modes
- backtest and live differ only in adapter implementation
- order lifecycle is runtime-owned, not strategy-owned
- switching between backtest and live is done by config only
